## 1. Summary

bw-core is the **business-wallet orchestration layer**: a component that
runs configurable business logic — flows that involve **authentication,
verification, and issuance** — over a set of primitives, embedding
`siros-issuer-core` and `siros-verifier-core` as libraries.

The term "business wallet" (WE BUILD usage) covers the combined features
of an issuer, a wallet, and a verifier, **plus an orchestration layer** on
top of the three. bw-core is that orchestration layer. A business wallet
also groups multiple wallet instances via WMP; WMP is the carrier for
that instance orchestration and one of bw-core's wallet-facing carriers
(§7) — the employee's personal PID wallet is reached over OpenID4VP /
OpenID4VCI deep links or the DC API, never WMP.

What bw-core is **not**:

- not a general workflow engine — the flow language is deliberately
  **non-Turing-complete** (§5);
- not a second implementation of any protocol — every cryptographic
  verb (present, verify, sign, issue) is a library call into a core;
- not a trust decision point — all trust is go-trust's (§9);
- not a place where subject data transits in plaintext (§10);
- not a derivation point for pseudonyms or any subject identifier — the
  wallet derives, bw-core compares (§8).

## 2. Background and motivation

### 2.1 The flows neither core covers

The issuer-core session state machine covers *one credential, one wallet,
one redemption*. The verifier-core request/response covers *one
presentation, one verifier session*. Real business flows compose both,
across roles, with data movement between the steps:

1. **Company-bound SCA:** present a PID **and** a PoA (or EUCC) in one
   transaction; check the PoA is **bound to the PID's subject**; issue an
   SCA bound to the company. Neither core performs the cross-credential
   check, and the issuance subject derives from *two* presentations.
2. **Identity-bound EUCC:** an identity-bound session (the business
   wallet knows who its user is); present a PID; issue an EUCC **only if
   the PID's identity is the same identity the session knows**.
3. **Payment receipt:** present a PoA and an SCA (direct payment); issue
   a Payment Receipt attestation over the payment facts.
4. **Token-sourced attestation:** extract claims from a SAML or OIDC
   token (an enterprise IdP login) to generate an attestation — and
   request a PID presentation as part of the same flow.

Each of these is a *sequence*: request presentation(s) → verify →
cross-check → derive subject data → issue → notify. Sequencing is policy,
not protocol: it belongs in **configuration**, over **primitives**, with
the cryptography in libraries. That is bw-core.

### 2.2 Precedents inside the family

- issuer-core's **Mode B** already embeds verifier-core in-process for a
  presentation-then-issue sequence — but hardcoded to exactly one shape
  (present PID → bind session → mint code). bw-core generalizes the
  *composition*, not the cryptography.
- The **ZK rulebook layer** (issuer-core §8.3) already answers "configure
  behavior with minimal code changes" for derivations: rulebooks are
  TOML data over a derivation vocabulary. bw-core applies the same
  discipline to *flows*: flow definitions are data over a step
  vocabulary (§5–6).
- **pyFF/goFF** answer it for pipelines: a linear sequence of
  closed-vocabulary actions over a working set, with bounded `fork`/`map`
  sub-pipelines, labels, and `end` — fifteen years of federation-ops
  proof that a *small, closed* action vocabulary beats an embedded
  scripting language. bw-core's flow language is that shape (§5).

### 2.3 WE BUILD context

The WE BUILD consortium's BU/PA-group flows are the concrete demand
(complex-flow documentation lives in the `webuild-consortium` BU and PA
repositories; "business wallet" there means exactly issuer+wallet+verifier
plus orchestration). The architecture ADRs relevant here:

- **ADR 002 (identity matching):** cross-border identity matching is
  **deterministic**: PID `id` and a new `nonce` are both mandatory and
  both generated by the PID Provider; the **wallet** derives from the
  nonce a stable pseudonym unique to the identity *and* the relying
  party; the derivation mechanism and its lifecycle are "defined
  separately"; name/date-of-birth matching is explicitly rejected as
  probabilistic. Two consequences shape §8: bw-core's checks are exact
  math, never heuristics; and the nonce is a wallet-side value, so
  bw-core **never derives** a pseudonym from presented claims — an RP
  holding the nonce could compute every other RP's pseudonym. bw-core
  compares a pseudonym the wallet presents.
- The BU/PA rulebooks (attestation-rulebooks-catalog) are the source of
  the concrete credential definitions flows will reference.

## 3. Goals and non-goals

### 3.1 Goals

1. **Flows as data over primitives.** A flow definition is a document in
   a non-Turing-complete language (§5) interpreted by a fixed engine.
   Adding a new business flow = writing a flow definition + possibly a
   plugin — not forking the engine.
2. **A closed primitive vocabulary** (§6) that closes over §2.1's flows
   and the obvious near-term extensions, with the same exit criterion as
   the rulebook layer: *a new flow needs no engine changes unless it needs
   a new primitive*.
3. **Pluggable carriers, WMP for instance orchestration** (§7): a
   wallet-facing step rides the carrier its target speaks — deep link /
   QR, the W3C DC API, or WMP; the business wallet's instance-grouping
   selects which WMP instance(s) a step addresses.
4. **Deterministic identity-binding checks** (§8) as first-class
   primitives — the cross-credential glue (PoA↔PID, session↔PID) the
   flows need.
5. **The security disciplines carry up a level unchanged** (§10):
   sealed subject data, PII never in logs/errors, fail-closed trust,
   stable machine-readable refusal codes.

### 3.2 Non-goals

- **No general computation.** No loops, no recursion, no
  expression-language escape hatch. Conditional logic is declarative
  matchers; iteration is bounded `map` over a list known at
  flow-definition time. If a flow needs real computation, it needs a
  plugin (which is code, reviewed as code).
- **No second protocol implementations.** OID4VCI, OID4VP, DCQL, COSE,
  status lists: library calls. bw-core never re-does JOSE.
- **No trust logic.** The PDP owns every allow/refuse (§9); bw-core
  constructs the evidence.
- **No UI.** The business wallet frontend is a separate concern; bw-core
  exposes the same SSE/event surface shape issuer-core does (§8.6), and
  carrier messages.

### 3.3 Explicit scope guards

- A flow definition **cannot** import code, reference files outside its
  plugin allowlist, or call endpoints outside its configured targets.
- A plugin **cannot** be defined in a flow document; plugins are
  deployment config + reviewed code.
- The engine **rejects** unknown step kinds, unknown matchers, unknown
  encodings — fail-closed with stable codes, exactly as the circuit
  catalog does.

## 4. Architecture

### 4.1 Component overview

```
                   ┌─────────────────────────────────────────┐
                   │                bw-core                   │
                   │                                         │
 business wallet ──┤  flow language  ──▶ flow engine ──┐      │
 frontend (SSE)    │  (definitions)     (interpreter) │      │
                   │        │                        │      │
                   │  FlowStore (trait)               ▼      │
                   │        │              ┌──────────────┐│
                   │        │              │  primitives   ││
                   │        │              └──────────────┘│
                   │                       │        │       │
                   │        ┌──────────────┘        │       │
                   │        ▼                       ▼       │
                   │  siros-verifier-core    siros-issuer-core
                   │  (present, verify)      (issue, sign, status)
                   │        │                       │       │
                   │        └───────── go-trust ────┘       │
                   │                  (PDP)                │
                   └─────────────────────────────────────────┘
                        ▲                                │
                        │ carriers: deep link / DC API / WMP
                   wallet instances (personal/business) ──┘
```

- **Flow engine:** loads definitions, instantiates flows, sequences
  steps, owns flow state, emits events. One engine, many definitions.
- **Primitives:** step-kind implementations (§6), each a small, tested
  unit calling core/PDP/plugin surfaces.
- **FlowStore:** pluggable persistence (§8.3) — in-memory reference,
  MongoDB production; same trait discipline as `SessionStore`.
- **Carriers:** the wallet-facing transports (§7) — deep link / QR and
  the DC API through the cores' existing request builders, WMP through a
  `wmp.flow.*` adapter.

New repo `sirosfoundation/siros-bw-core`:

```
│   ├── context.rs                   # the working set (§5.3)
│   └── error.rs                     # stable refusal codes
├── service/                         # deployable binary
│   ├── src/

│   │   ├── plugins/                 # fetch/token/notify provider traits + impls
│   │   ├── carriers/                # deeplink.rs, dcapi.rs, wmp.rs (§7)
│   │   ├── store.rs / mongo_store.rs

│   └── tests/
├── flows/                           # reviewed flow definitions (fixtures + shipped)
└── testdata/
```

The sans-I/O split mirrors the issuer-core discipline: the language, the
engine's transition logic, the binding checks, and the context are pure
and testable without I/O; effects cross primitive boundaries only.

### 4.3 Embedding vs deploying the cores

**Recommended: embed in-process** (library calls into both cores), as
Mode B already does. Deployment alternatives (sidecar HTTP to
issuer/verifier services) are config-selected but not the reference path —
in-process keeps subject data off the network between flow steps, which
is a load-bearing privacy property (§10).

## 5. The flow language

### 5.1 Shape (pyFF/goFF-inspired)

A flow definition is a **pipeline**: a linear document of steps over a
working set. goFF runs the same pipeline YAML as pyFF — the portability
lesson matters here: the language is small enough to be *stable*, and
definitions are data that outlive engine versions.

```yaml
# flows/company-sca.yaml — §2.1 flow 1, as an illustration
flow: company-sca
description: >
  Present PID + PoA, check the PoA binds to the PID's subject,
  issue a company-bound SCA.

context:
  issuer: https://bw.example.org           # who we act as
  audience:  https://bw.example.org/flows/company-sca

steps:
  - presentation:
      id: pid-and-poa
      request:                             # DCQL; one transaction
        credentials:
          - id: pid
            format: dc+sd-jwt
            meta: { vct_values: [urn:eudi:pid:1] }
            claims: [{ path: [id] }, { path: [given_name] }, { path: [family_name] }]
          - id: poa
            format: dc+sd-jwt
            meta: { vct_values: [urn:ewb:poa:1] }
            claims:
              - { path: [attorney_full_name] }
              - { path: [company_statutory_full_name] }
              - { path: [euid_reference] }
      require: [pid, poa]

  - bind:
      id: poa-attorney-is-pid-subject
      primitive: claim-equals                              # deterministic (§8)
      left:  { step: pid-and-poa, credential: poa, path: [attorney_pid_id] }  # (!) placeholder, see note
      right: { step: pid-and-poa, credential: pid, path: [id] }
      on_mismatch: fail

  - issuance:
      credential: urn:ewb:sca:1
      subject:
        from: { step: pid-and-poa, credential: pid }       # base subject = PID claims
        merge:
          company: { step: pid-and-poa, credential: poa, path: [company_statutory_full_name] }
      notify: [wallet]
```

> **Review note (2026-11-09) — the headline flow's binding is not yet
> expressible.** The `bind` step above assumes the PoA identifies its
> attorney by the PID `id`; `attorney_pid_id` is a placeholder, no such
> claim exists. The WE BUILD PoA as deployed
> (`sirosid-dev/fixtures/vc-presentation-requests/eu_business_wallet.yaml`)
> identifies the attorney by `attorney_full_name` only — no key, no
> identifier. v0.1 used `same-key` here (PoA holder key = PID `cnf`);
> under the ARF every attestation carries its own key, so a PoA and a
> PID sharing a holder key is the exception, not the strongest check.
> The honest binding against today's credential is a name comparison,
> which is what ADR 002 rejects and which needs the string composition
> §5.4 forbids. Decision needed (§14 Q11): (a) ask the PoA rulebook to
> carry the representative's PID `id` or RP-scoped pseudonym; or (b)
> accept a pilot-only `rule-match`-on-names plugin, labelled as such.

Read it as: *steps transform a working set; matchers select what a step
sees; nothing computes.* The schema details follow in §5.2–§5.3.

### 5.2 What the goFF/pyFF shape actually teaches

Reading the goFF examples beyond the minimal one: `load` is not a
privileged header — `finalize-aggregate.yaml` interleaves load/select pairs
mid-pipeline, aliasing each source's snapshot (`select as /swamid`) and
selecting from aliases later (`/swamid!//…`); `mdq-server-pipeline.yaml`
scopes the entire pipeline under `when update:` with three sibling `fork:`
bodies each carrying nested sub-pipelines; `fork-idp-sp.yaml` forks twice
and continues after. The pipeline is a **flat sequence of heterogeneous
steps with scoped control wrappers and named working-set snapshots** —
exactly the shape bw-core needs, minus XML:

- **steps interleave freely** — a `presentation` step can appear before
  *and* after an `issuance` step in one flow (present PID → match → issue
  → present the issued credential onward is a real flow shape);
- **`as`-style aliases** name a step's results for later reference
  (`store as /company` ↔ our step-id context keys — same idea; step ids
  are the v1 names, `as` is not in v1, §14 Q9);
- **`when:` wrappers scope** a body by mode/condition (the `when:`
  conditions bw-core needs are match-results and flow modes, not pyFF's
  request-scoped ones — goFF deprecated those);
- **`fork:` runs isolated sub-pipelines** over copies of the context —
  bounded, with a documented sandbox discipline (changes don't leak
  out). The shape to port *if* a flow needs it; not a v1 construct
  (§5.4, §14 Q9).

### 5.3 Language decision (pinned)

**Resolved (2026-11-08):**

- **Flow definitions are YAML.** The goFF/pyFF precedent is decisive:
  the pipeline shape is a *top-level list of heterogeneous maps*
  (`- presentation: …` / `- bind: …`), with control wrappers
  (`when:`, `fork:`, `map:`) nesting bodies under a key — natural
  YAML, awkward TOML (`[[steps]]` + dotted-path child tables read
  flat and re-parent painfully). Definitions are human-authored
  *policy documents people argue about*: nesting and inline comments
  win. The YAML footgun class (no/1:30/Norway) is mitigated by the
  strict schema — fail-closed unknown-kind refusals, typed scalars
  (§5.4).
- **Deployment config stays TOML.** Plugins, allowlists, provider
  endpoints, store settings — the family convention
  (`[zk.rulebooks.<name>]` etc.) unchanged.
- **The schema is defined as a JSON tree.** YAML and TOML are two
  frontends to one parsed-document schema; a flow definition parses to
  a typed JSON document which the loader validates against the
  language schema. Future-proofs *generated* definitions (emit JSON or
  YAML), makes the language schema itself a JSON(-Schema-like) artifact,
  and keeps the engine frontend-agnostic (the §5.1 sketch maps 1:1).

### 5.4 Non-Turing-complete by construction

The language offers exactly these control constructs, all bounded:

- **linear steps** — always run in document order;
- **`map:`** — bounded iteration over a *list in the context*, not over
  computed output (goFF's `map` shape: per-item sub-pipeline, isolated
  snapshot, side effects per item);
- **`when:` matchers** — declarative preconditions on a step (string/set
  membership, presence, equality — the same matcher vocabulary everywhere,
  no expressions);
- **`end:`** — early flow-stop (goFF/pyFF `break`/`end`).

**Not in v1** (resolved 2026-11-09, §14 Q9): `fork:` and `as` aliases.
Step ids are the only names; a flow that needs an isolated sub-pipeline
is the signal to add `fork:` in a later language version, not to
emulate it.

Explicitly absent: variables, arithmetic, string interpolation, loops
over runtime-computed collections, recursion, user-defined functions. A
definition that needs any of them is asking for a **plugin primitive**
(§6.7), which is reviewed code with tests — the same boundary the ZK
layer draws ("a rulebook translates to code *and sometimes config*, or
both").

Three schema rules that fall out of the above:

- **Paths are DCQL claims-path arrays**, never dotted strings. mdoc
  namespaces contain dots (`org.iso.18013.5.1`), so a dotted
  `pid-and-poa.poa.company` is ambiguous the moment a flow touches an
  mdoc. A context reference is a typed object — `{step, credential,
  path: [...]}` — with the `path` semantics the `presentation` step's
  DCQL request and the TS11 catalog already use; the format-aware
  lookup is issuer-core's `lookup_claim_path` (mdoc literal namespace
  key first, SD-JWT nested).
- **Mismatch handling is explicit.** A `bind` step carries
  `on_mismatch: fail | record` (default `fail`): `fail` ends the flow
  with the primitive's refusal code; `record` writes `matched: false`
  for a later `when:` to branch on. Branching is visible in the
  definition, never implied.
- **Every definition carries `language_version` and has a content
  digest.** Unknown versions are refused at load (the circuit-catalog
  discipline). The digest travels in the PDP evidence (§9) so policy
  can pin reviewed definitions, the way it pins circuits.

### 5.5 The working set (context)

pyFF's working set is the entity selection; bw-core's is the **flow
context** — a typed document the engine owns:

- **inputs** (fixed at flow start): flow id, initiating session identity
  (when the business wallet knows its user), carrier target / WMP
  instance selector, caller-supplied parameters;
- **presentation results**, keyed by step id: each entry carries the
  *verified claims* (as a claims object, format-tagged), the holder key
  (`cnf`/`DeviceKey`), and the credential identifiers presented;
- **derived values** written by steps (`store`, `token`, `fetch`);
- **issuance refs**: session ids / offer URIs created by `issuance`.

The context **is** persisted between steps — a `presentation` step waits
on a human, a deferred `issuance` can wait days — so "in memory only" is
not a property it can have. The property it has is a **clear/sealed
split** of the `FlowStore` record (§8.6). In the clear: flow id,
definition digest, step cursor, per-step state, armed response handles,
timestamps, and bind verdicts (`matched`, primitive name, parameters —
never values). Sealed under a per-flow data key in the vault: everything
subject-shaped (presentation claims, holder keys, derived values, caller
inputs). The engine unseals into memory for one step and re-seals; the
plaintext context is never logged and never leaves the process (§10).

## 6. Primitives (the step-kind vocabulary, v1)

Each kind is a primitive: implemented once, tested against a core-level
oracle, usable in any flow. **Closures over §2.1:**

| kind | does | calls | §2.1 flow |
|---|---|---|---|
| `presentation` | build a DCQL request, send it over the step's carrier, collect + verify responses | verifier-core `create_request`/`process_response` | 1,2,3,4 |
| `bind` | deterministic identity-binding checks (§8) | local (context only) | 1,2 |
| `issuance` | create an issuance session over derived subject data | issuer-core session API (in-process) | all |
| `token` | extract claims from a verified JWT-shaped token (OIDC ID token, JWT assertion) | plugins (§6.7) | 4 |
| `fetch` | call an external API for supplementary data | plugins | 3,4 |
| `store` | write a derived value into the context | local | all |
| `notify` | emit a carrier message / SSE event | carrier adapter | all |

Two rules keep the vocabulary honest:

1. **A primitive never decides trust.** `presentation` verifies
   cryptography; the *acceptability* of a presented credential is a PDP
   call the engine makes on the primitive's evidence (§9). `bind`
   performs *math* on context values — it refuses mismatches, it does not
   consult policy.
2. **A primitive never invents data.** Output shapes are fixed by the
   kind; a step cannot reshape context arbitrarily (`store` writes a
   value under a declared key, with a declared encoding).

### 6.1 `presentation`

- Declares one or more DCQL **credential queries** (derived from the
  flow's credential ids, or explicit DCQL for the odd cases).
- One **transaction** per step: multi-query presentations ride one
  OID4VP request/response, so the "PID and PoA presented together"
  guarantee is cryptographic (one nonce, one audience, one key-binding
  proof per credential) rather than sequential. Multiple `presentation`
  steps in a flow are *separate* transactions — flows that need
  cross-presentation same-party guarantees add a `bind` step. Note what
  one transaction proves: the same wallet answered both queries. It
  does not prove the two credentials describe the same subject; that is
  `bind`'s job.
- Verification is verifier-core in-process; trust in each presented
  credential goes to the PDP (`permit_presentation`, the Mode B pattern),
  fail-closed.
- **Correlation** is the opaque challenge handle in the request's
  `response_uri` (the Mode B `challenge_handle` pattern) plus the
  nonce/audience the wallet signs into the key-binding proof. There is
  no DPoP here: DPoP binds a wallet key to a *token endpoint*, which a
  presentation step does not have. Mode B needs DPoP only because the
  same wallet later redeems a code at `/token`. (v0.1 had DPoP "riding
  WMP the same way it rides Mode B's challenge"; that was a category
  error.)
- The carrier (§7) decides how the request reaches the wallet: a
  `request_uri` in a deep link / QR, a DC API request (verifier-core's
  `create_dc_api_request`), or a WMP `oid4vp` flow start carrying
  `request_uri_ref`. The response path is OID4VP's own
  (`direct_post.jwt` to the `response_uri`, or the DC API response) in
  every case.
- **Dependency:** verifier-core's `process_response` currently refuses
  DCQL `credential_sets` (`src/oid4vp.rs`, "not supported in the
  spike"). P-bw2's multi-query presentations need either that lifted or
  a documented restriction to plain `credentials` arrays.

### 6.2 `bind` — see §8.

### 6.3 `issuance`

- Creates an **issuer-core session in-process** (the same session
  record, store, and state machine — not a second issuance path).
- Subject data derives **declaratively** from the context: a `from`
  (base presentation) plus a `merge` map (context paths → claim paths).
  No computation, no plugins — a mismatch of shapes is a refusal at
  definition-validation time where checkable, at runtime otherwise.
- The pre-auth offer or authorization challenge rides the step's
  carrier back to the target wallet (§7): a credential-offer deep link /
  QR, or a WMP `oid4vci` flow start carrying `credential_offer_uri`.
- Rate limiting, retention, sweeping: issuer-core's machinery, reused,
  not reimplemented.

### 6.4 `token`

A verified JWT-shaped token → claims: an OIDC ID token, an RFC 7523
assertion, an enterprise IdP's JWT. The token arrives via a carrier
message (a business system presenting its IdP assertion) or as a flow
input. Plugin-verified (signature, audience, freshness windows — the
checks `verify_private_key_jwt` performs in issuer-core, generalized),
claims into the context under the step id. **The plugin trait is the
reviewed code; the flow only references the plugin by name.**

**SAML is out of the Rust core.** XML-DSig verification is a different
attack surface (canonicalization, XXE, signature wrapping) and v0.1's
"the same checks as `verify_private_key_jwt`" understated it. An
integrator that already runs a SAML SP asserts the user the way
issuer-core Mode A already allows — the flow consumes the integrator's
assertion as a flow input. §2.1 flow 4 is therefore "integrator-asserted
identity + PID presentation", not a SAML parser in bw-core.

### 6.5 `fetch`

External API → context value. Bounded: config-selected provider by name,
timeout, response-size budget, **no subject data out** unless the
provider's config declares it (the PII-flow audit discipline, §10). The
step declares its **inputs** (the context paths it may send) as well as
its output key, so the PII flow of a definition is checkable at load
time from the definition and the provider allowlist alone, not only at
runtime. Fail-closed on error — a failed fetch fails the flow step,
never silently continues.

### 6.6 `store` / `notify`

`store` writes a context value under a declared key (validated against
the definition's own schema of what steps may read). `notify` emits a
carrier message to the flow's target (a WMP notification when the
target is an instance) or a typed SSE event for the embedding frontend — the "one state machine, two audiences" shape again.

### 6.7 Plugins

`token`, `fetch`, and any future exotic primitives take **plugins**:
`trait FlowPlugin` with a small surface (name → invoke(context) →
value). Plugins are *code*: reviewed, tested, allowlisted in deployment
config. A flow definition referencing a plugin not in the allowlist is a
startup refusal. This is the deliberate Turing-completeness escape
hatch: **code stays code, config stays config** — the same boundary the
ZK rulebook layer draws.

## 7. Carriers; WMP as the instance-orchestration carrier

v0.1 said "WMP is **the** wallet-facing carrier, not a side-channel".
That conflated three relationships with different protocols and
different data-visibility rules. Stated separately:

| relationship | protocol | bw-core's role |
|---|---|---|
| **(a)** the business wallet's own instances ↔ their backend | WMP, `wmp` profile, `wmp.flow.*` with the openid4x flow types | the WMP **orchestrator** side — or a peer of it (open, below) |
| **(b)** business wallet ↔ another organisation | WMP (`wmp` or `scc` profile), eDelivery | sender / recipient of messages and evidence |
| **(c)** the employee's **personal** PID wallet | OpenID4VP / OpenID4VCI over deep link / QR, or the DC API | ordinary verifier / issuer |

Flows 1, 2 and 4 all involve (c): a third-party EUDI wallet does not
speak WMP. P-bw1 to P-bw3 ship before WMP lands (§13), so a non-WMP
carrier exists by construction. Hence:

- **Carriers are pluggable.** A wallet-facing step names a carrier
  (`deeplink`, `dc_api`, `wmp`) or inherits the flow's default; the
  step's semantics do not change with the carrier. Two of the three
  already exist in the cores (`create_request`, `create_dc_api_request`,
  the offer-URI builders); the WMP adapter is the new code.
- **WMP as carrier means `wmp.flow.*`, not a private scheme.** WMP Core
  §6 defines structured flows with `flow_id`, progress, action,
  complete, error and cancel; the openid4x profile defines the `oid4vp`
  flow (start carries `request_uri_ref` or `dcql_query`) and the
  `oid4vci` flow (start carries `credential_offer_uri`). A bw-core
  presentation step over WMP *is* a `wmp.flow.start` of type `oid4vp`;
  correlation is WMP's `flow_id` plus the OID4VP challenge handle
  (§6.1). v0.1's "flow correlation by challenge handle, generalized"
  reinvented `flow_id`.
- **Orchestration carrier:** the business wallet groups multiple wallet
  instances (personal wallet of the employee, business instance, etc.);
  a flow's **instance selector** routes each WMP-carried step to the
  right instance(s). A flow may present to instance A and deliver the
  issued credential to instance B. WMP identifiers (`did:`,
  `x509:san:dns:`, `ebcore:iso6523:`) name parties, not instances; the
  selector grammar therefore sits on the backend's instance registry
  (the wallet-instance lifecycle), and the selector is an
  **authorisation surface** — who may address which instance is a PDP
  question (§9), not a flow-input convention.

**Two boundaries this section must draw, not assume:**

1. **Verifier role vs orchestrator role.** The openid4x profile forbids
   the orchestrator from learning which credential a wallet chose, how
   many could answer, or which claims were disclosed (`match` result
   §3.3.3, `select_credentials` §3.2.3.1 — closed sets, refusal on any
   extra member). bw-core *as verifier* legitimately receives the
   claims at its `response_uri`. The two roles have opposite
   data-visibility properties. If one process hosts both for the
   business instances, the design needs an explicit internal boundary
   (separate types; no shared context between the orchestrator's flow
   record and the verifier's presentation result).
2. **The holder role.** §1 says a business wallet is issuer + wallet +
   verifier, but §6 has no holder primitive: nothing in this design
   answers an inbound OID4VP request from a bank to the business
   wallet, or signs a presentation with a business-instance key. Either
   bw-core delegates holding entirely to WMP instances — then the
   orchestrator is go-wallet-backend / the planned Rust WMP engine and
   bw-core is a **WMP peer** that starts flows on instances — or
   bw-core includes the orchestrator. The Rust-engine spec left WMP
   client-crate ownership open; whichever way this falls, there is one
   WMP crate, shared, not two.

> **Review note (2026-11-09):** the holder-role / orchestrator boundary
> is the largest open architectural question in this document (§14
> Q10). The §13 phasing can start without it — P-bw1 to P-bw3 are
> carrier (c) — P-bw4 cannot.

**Naming collision:** the openid4x profile's `match` flow type means
*local credential matching in the wallet*. This document therefore
uses `bind` for identity binding (§8) and never `match` as a step kind.

**Open (§14 Q4):** which WMP profile on which relationship — `wmp` for
(a), `scc` or `wmp` for (b) — and the instance-selector grammar.

## 8. Identity binding — the generic concept, bind primitives

### 8.1 What it is

**Identity binding is the generic concept**: *does this presented
credential describe the same subject as this session (or this other
credential)?* The answer is assembled from **bind primitives** — small,
deterministic, composable checks the flow language names. Pseudonym
comparison is **one** way to do that, not the concept: not every
credential carries a pseudonym (non-PID credentials, EUCCs, SCAs), and
not every session-to-credential binding can use one (the session may
know the subject only under different attributes, from a different
authority).

Mode B has none of this; it is the genuinely new primitive family.
("Identity match" in v0.1; renamed to avoid WMP's `match` flow type, §7.)

### 8.2 The built-in bind vocabulary (v1)

Each primitive is a pure function over the context (presentation claims,
holder keys, session-known data), with a stable refusal code on mismatch:

| primitive | semantics |
|---|---|
| `same-key` | both presentations' holder keys (`cnf.jwk`/`DeviceKey`) are the same key (by thumbprint). Exact, but **narrowly applicable**: under the ARF each attestation carries its own key, so two credentials sharing a holder key is the exception (same-batch issuance to one WSCD key, or a deployment that chooses it). Use it when the credentials' rulebooks guarantee it — not as the default cross-credential check v0.1 made it |
| `claim-equals(a, b)` | the claim at context path `a` equals the value at path `b` (or a caller-supplied literal) — exact, format-aware path lookup (mdoc literal-key first, SD-JWT nested), mdoc full-date unwrap. Paths are DCQL path arrays (§5.4) |
| `pseudonym-equals` | a pseudonym the **wallet presented** — a claim such as the ADR 002 RP-scoped pseudonym, or a ZK public output such as nym_auth's — equals the value the session knows for this subject under this RP scope. The engine compares; it **never derives**. Replaces v0.1's `claims-hash`, which hashed `id` + `nonce` on the engine side: ADR 002 makes the wallet the deriver and the nonce a value no RP may hold, and nym_auth already is the derivation rulebook (issuer-core §8.3) |
| `rule-match` | a **rule** (claim path → expected value) supplied by the flow's initiating caller, evaluated against one presentation — vc's `IdentityMatch` semantics (Appendix B), the issuer-core §6.5 port generalized to any flow step |

Determinism is mandatory (ADR 002's rejection of fuzzy attribute
matching): every primitive is exact math; **no heuristics in the
vocabulary**, and a primitive that cannot resolve declares mismatch,
never best-effort. `rule-match` on name attributes is *exact as a
comparison* but *probabilistic as identity evidence*; a flow that
relies on it says so (§5.1 review note, §14 Q11).

### 8.3 User-space hooks (the easy bind-primitive path)

Built-ins never close the space: real deployments bind on
attribute-shapes the vocabulary does not know (national identifiers,
organizational ids, derived keys). The flow language therefore has a
**first-class bind-primitive extension point**:

```rust
/// One user-space bind primitive (the easy hook).
trait BindPrimitive {
    /// The name the flow language references (`primitive: <name>`).
    fn name(&self) -> &'static str;
    /// Evaluate: claims of the presentation(s) + the session-known
    /// data → verdict + recorded evidence (never raw values).
    fn bind(&self, inputs: BindInputs<'_>) -> Result<BindVerdict>;
}
```

- **Implementing one is deliberately trivial**: one struct, a name, a
  `bind` over typed inputs (presentation claims by step id, holder
  keys, session data) returning a verdict. No engine internals, no
  lifecycle, no I/O surface — user-space code stays small enough to
  review by inspection.
- Registered by name in deployment config, **allowlisted** per flow
  (a flow referencing an unregistered primitive is a load refusal — the
  plugin-allowlist discipline, §6.7).
- The engine treats a user-space primitive **exactly like a built-in**:
  same evidence recording (verdict + primitive name + parameters, never
  claim values), same refusal codes, same trust placement — a bind
  primitive performs *math*, it never decides trust (§9).

### 8.4 Where the check sits in a flow

```yaml
  - bind:
      id: pid-is-session-user
      primitive: pseudonym-equals          # or a user-space name
      left:    { step: present-pid, credential: pid, path: [pseudonym] }
      against: session.subject.pseudonym   # what the session knows
      scope:   rp                          # the RP scope the wallet derived for
      on_mismatch: fail                    # default; `record` to branch on it
```

The step records `matched: true/false` (plus primitive name and
parameters, never values) in the context; the following steps' `when:`
matchers consume it when `on_mismatch: record`. The default is
fail-closed with a stable code; branching is opt-in and visible (§5.4).

### 8.5 Relationship to the issuer-core §6.5 work

The pre-auth PID-present→bind→issue flow is **flow #1 in miniature** and
lands twice, deliberately:

1. **In issuer-core now** (in progress): config-gated, conformance
   profile untouched — the state machine already enforces
   presentation-before-redemption (a bound session starts
   `awaiting_authorization`; `claim_pre_auth_code` requires `offered`).
   No new states; the challenge machinery is reused. The rule shape is
   `rule-match` (vc's `IdentityMatch` port).
2. **Absorbed by bw-core** at P-bw1: the same flow as a
   `presentation → bind → issuance` pipeline, with the issuer-core gate
   remaining for pure-issuer deployments.

### 8.6 Flow state machine + store

- One state machine per flow *instance* in the core (`engine.rs`). v0.1
  named the states `pending → presenting → matching → issuing →
  issued`, which is flow #1 spelled out and contradicts §5.2 (steps
  interleave; a flow may present, issue, then present again). The
  lifecycle is therefore **generic** and the position in the definition
  is data:
  - lifecycle: `created → running ⇄ waiting → completed | failed |
    expired`, where `waiting` means a response-bearing step has armed a
    handle and the engine is parked on it;
  - position: the **step cursor** (index into the definition, plus the
    `map:` item index when inside one) and a **per-step state**
    (`pending | armed | done | failed`) keyed by step id;
  - illegal transitions refused with stable codes — the `session.rs`
    discipline, new machine.
- `FlowStore` trait: `insert`, `get`, `step` (advance cursor +
  transition, CAS on the record version), `arm/take` per
  response-bearing step (the `ModeBState`/`transaction` CAS
  discipline), `sweep`. In-memory reference + MongoDB production, behind
  `--features mongo` exactly as issuer-core. The record's clear/sealed
  split is §5.5.
- Events: the SSE stream shape (`(unix, state)` transitions + typed
  payload events) for the embedding frontend, plus carrier
  notifications (WMP `wmp.flow.progress` when the target is an
  instance).

## 9. Trust boundary

Unchanged from the family discipline, stated once:

- **go-trust decides, fail-closed.** Every *acceptability* question —
  may this flow run for this caller, may this presented credential be
  trusted, may this issuance proceed — is an AuthZEN query
  (`IssuanceTrustQuery`, `TrustQuery`, `WalletProviderTrustQuery` — the
  three existing decisions; flows may add evidence fields, not new
  decision bypasses).
- **The evidence names the definition.** Every flow-level query carries
  `flow_id`, `language_version` and the definition's content digest
  (§5.4), so a deployment can permit only reviewed definitions — the
  pin the circuit catalog gives circuits. This is also the answer to
  §14 Q3: PDP calls sit at the engine boundary, and a flow that wants a
  visible policy gate expresses it as `when:` over recorded evidence.
- **Bindings are not trust.** `same-key`/`pseudonym-equals` are math;
  the PDP never sees them, and they never substitute for a trust
  decision. A deployment wanting *policy over bindings* (e.g. "accept
  `pseudonym-equals` only for MS X") expresses it as PDP rules over the
  binding *result* recorded in the evidence.

## 10. Security and PII properties

Carried up from issuer-core, unchanged in spirit:

1. **Subject data is sealed at rest** (vault), including `rule-match`
   rule values and presentation claims — the clear/sealed record split
   of §5.5. The plaintext context exists in memory for one step, is
   never logged and never leaves the process.
2. **PII never transits error paths or logs** — refusals name paths and
   codes, never values.
3. **No standing subject index** — flow records key on handles, not
   subjects; the operator retains the flow↔subject mapping.
4. **Remote URLs are hostile I/O targets** — `fetch` providers enforce
   scheme/host policy, redirect caps, streaming budgets before
   allocation (verifier-core ts11 discipline).
5. **Stable machine-readable refusal codes** for every engine and
   primitive refusal.
6. **Signing through the Signer interface** — issuance inside flows uses
   issuer-core's signer (HSM-capable); bw-core adds no signing of its own.

## 11. Testing strategy

- **Fixture-backed flow definitions** (the goFF model): every shipped
  flow in `flows/` runs in CI against mock-core fixtures (recorded
  presentation responses, PDP doubles, plugin stubs) — a definition
  change is a visible diff against recorded output.
- **Core-level oracles**: presentation steps round-trip through
  verifier-core with real credentials (the wallet-core conformance
  fixtures); issuance rounds into verifier-core verification (the
  issuer-core P1 discipline).
- **Language tests**: every construct positive+negative, unknown-kind
  refusals, non-Turing-completeness guards (a definition with a
  computed `map` source is refused).
- **Definition identity tests**: digest stability across YAML
  re-serialization and JSON emission, `language_version` refusal, and
  the PDP evidence carrying the digest (§5.4, §9).
- **Conformance**: where WE BUILD publishes test-bed specs (the ITB),
  flow fixtures target them; the interop test bed is the external
  oracle.

## 12. Alternatives considered

- **Extend SUNET/vc's apigw instead** — vc's 48.6k LOC lives mostly in
  auth-provider plugins and the session machinery; adding a general flow
  language there couples business logic to a Go codebase we are
  replacing, and its plugin shape (Go interfaces) does not give the
  config/code boundary the ZK layer's exit criterion demands.
- **Temporal/Camunda/etc.** — general engines are Turing-complete by
  design, carry their own state stores and PII surfaces, and make the
  "subject data never transits the engine in plaintext" property
  unprovable. Rejected.
- **Compose via the existing HTTP surfaces (issuer-core +
  verifier-core as services)** — viable deployment mode, kept as a
  config option (§4.3), but in-process is the reference: fewer hops for
  sealed data, single trust boundary.
